The problem

Building an agent is easy. Getting agents to work together isn't.

Every team picks its own framework, and every agent ends up an island. A2A is the open protocol that fixes that. It gives agents one common way to talk: an agent publishes a card saying what it can do, another agent sends it a message, and it answers with a task it can stream, pause for input, and finish later.

But look at what that asks of you. To be called, an agent has to be an HTTP server somebody can reach. Which means:

SECURITY

An inbound rule

You open a port, get a public address, a DNS name and a certificate, and put authentication in front. Your agent, the thing holding your API keys and your tools, is now on the internet.

DURABILITY

A connection that has to survive

Agent tasks run for minutes or hours. HTTP connections don't. When the stream drops, whether the task survives depends on how each agent was written, and the caller is left guessing.

So the protocol solves how agents talk, and hands you two new problems.

How it's different

Not a tunnel. Not another agent gateway.

Kontra sits between two things you may already run, and takes the useful half of each.

TUNNELS

SSH, ngrok

A tunnel dials out too, and it gets a private agent a URL in a minute. But it forwards bytes. It doesn't know what an agent task is, so when either end drops the work is gone, and identity, access rules and history are yours to build.

AGENT GATEWAYS

agentgateway and others

A gateway is a proxy. It sits in front of agents it can already reach on the network, which suits agents that live together in one cluster. It has no way to an agent on a laptop, in another team's network or in another organisation, unless somebody opens one.

KONTRA

Outbound-only, and protocol-aware

The agent dials out, like a tunnel. The gate understands agent protocols, like a gateway. So agents that can't or shouldn't be exposed still get identity, access rules, durable tasks and a full record. Already run a gateway? Put it in front. They work together.

What Kontra does

One connector. It dials out, and that's the only connection there is.

Kontra keeps the part of a tunnel you want and fixes the rest. You run kontra connect next to your agent, and it reaches a gate that speaks A2A.

Nothing to open

No firewall rule, no port, no public IP. Your agent listens on localhost, or on a private network, and stays there.

The connector secures the link

Each node has its own identity key, and the gate decides who may call what. Seal a service end to end and the gate only ever stores ciphertext.

The gate speaks A2A

That's the difference. It knows what a task is, so it keeps every task and its whole conversation on record. A dropped connection stops being the end of the story.

Your agent doesn't change

No SDK, nothing to import. Stock A2A agents and MCP servers run as they are. Your agent doesn't know Kontra exists.

Here's what a dropped connection looks like.

Wifi drops in the middle of a task. The gate tells the caller it's waiting, your node redials on its own, and the gate asks the agent where they were. Notice the third line.

The caller can leave too. The task keeps running for up to 7 days, and the stream resumes from the last event they saw.

One thing to be clear about: Kontra holds the task, not your agent's memory. An agent that keeps its tasks in a database resumes after a crash. One that keeps them in memory won't.

Small agents, wired together

Stop building one giant agent.

There's a second thing this buys you, and it's the fun part. Once reaching an agent costs nothing, you start building small ones that each do one job well. Each is just a little A2A server on localhost, in whatever framework suits it. You give each one a name:

kontra connect \
  --serve a2a:recon=http://127.0.0.1:8001 \
  --serve a2a:triage=http://127.0.0.1:8002 \
  --serve a2a:report=http://127.0.0.1:8003
And now they can call each other, wherever they actually run, at localhost:7777/agents/<name>

Names instead of addresses

Move an agent to another machine and nothing that calls it changes.

Durable hand-offs

When triage hands a long job to report, it's a task the gate holds, not a connection somebody has to keep open.

A boundary per agent

The gate decides who may call each one, so the agent with the dangerous tools isn't reachable by everything else.

You can watch them talk

A local gate's console shows every call between your agents, on both legs. It's Burp history, but for agents.

Mix and match

A Python agent, a Go agent and a stock MCP server sit side by side. Add one more with another --serve.

Callable from any MCP client

The gate has its own MCP endpoint, so a stock MCP client can search for your agents, send one a message and follow the task.

Try it

Two steps.

First an agent with no Kontra anywhere, then a gate of your own in front of it.

1. An A2A agent

Any A2A server will do. The quickest is the A2A CLI, which turns a shell command into an agent.

go install github.com/a2aproject/a2a-cli@v0.3.1
mv "$(go env GOPATH)/bin/a2a-cli" "$(go env GOPATH)/bin/a2a"
export PATH="$PATH:$(go env GOPATH)/bin"

a2a server --exec 'echo Hello World' --port 9999 &
a2a send -a http://127.0.0.1:9999/.well-known/agent-card.json "hi"
→ Hello World
A working agent, reachable only from your own machine. That's the problem from the top of this page.

2. Your own gate

With Docker, bring a gate up on your machine and connect the agent to it.

git clone https://github.com/medmahmoudi26/kontra && cd kontra
docker compose -f compose.dev.yaml up -d --wait
go run ./cmd/kontra-gate migrate -f examples/local/kontra.yaml
go run ./cmd/kontra-gate serve -f examples/local/kontra.yaml &

go run ./cmd/kontra connect --gate http://127.0.0.1:8080 \
  --listen off --serve a2a:hello=http://127.0.0.1:9999 &

a2a send -a http://127.0.0.1:8080/agents/hello "hi"
→ Hello World, through the gate, as a task it keeps
Notice what didn't change: the agent. Same process, same port, still on localhost. Open http://127.0.0.1:8080/ to see the task.
